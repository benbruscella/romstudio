# Following the original audio microcode

The VR4300 CPU submits an audio command list to another processor: the **RSP**. The RSP has its own 32-bit scalar registers, eight-lane vector registers, 48-bit accumulators, and separate 4 KiB instruction and data memories. Its instruction words are different from the CPU's, even though some scalar operations look familiar.

ROM Studio translates both processors separately. [`transpiler/rsp.ts`](../../../../transpiler/rsp.ts) decodes original RSP words during recovery and emits static functions. [`runtime/rsp.ts`](../../../../runtime/rsp.ts) and [`rsp-vector.ts`](../../../../runtime/rsp-vector.ts) provide architectural operations. [`systems/n64/signal.ts`](../../../../systems/n64/signal.ts) supplies SP registers and DMA. In this **reference tier**, no audio command is replaced with a host implementation of that command. The **play tier** runs ROM Studio's TypeScript implementation of this exact microcode instead; see [the play-tier implementation](#play-tier-the-audio-microcode-in-typescript-10-november) below and [execution tiers](../../../../../docs/ARCHITECTURE.md#execution-tiers).

## The bounded audio study

`npm run cli -- boot --title sm64` first verifies CPU startup and records the exact SP start command, registers, RDRAM and SP memories. It then pauses the CPU and runs that first audio task in a separate, explicitly declared device fixture. A fresh replay executes only generated static RSP functions. The comparison includes scalar/vector state, accumulator slices and flags, all RDRAM and SP bytes, DMA, interrupt state and the functional clock.

The microcode loads itself, reads the original command list, writes output through DMA, sets its task-done signal and executes `BREAK`. This proves a bounded task executes; silent startup samples do not prove working game music. The study records its evidence under `dist/work/games/n64/sm64/analysis/startup/`, including `rsp/program.js`. The generated RSP explanation is under `game-code/rsp/`, using **IMEM offsets**, a different address space from CPU addresses such as `$80241800`.

## A readable mixer

[`code/audio.ts`](../code/audio.ts) explains the original `MIXER` handler as a sample loop. Each output combines the existing destination with a scaled input. A fractional rounding term survives the multiply and multiply-add; saturation happens after accumulation. Clipping an intermediate result would produce different samples.

The recovery checks select the handler through the cartridge's own dispatch table. Fifteen isolated fixtures cover empty buffers, one and three loop iterations, positive/negative/zero gain, signed extremes, fractional results and saturation. They compare 320 nonzero/edge-case sample positions against the named explanation, check that input samples survive, and guard the output boundaries. Both original-word execution and static replay must pass. These are declared analysis inputs rather than a claim that the game naturally emitted those commands at startup.

## Full-route PCM comparison

The current title-to-opening verifier additionally observes the AI output during both original-word execution and generated replay. Each stereo sample contributes its left value, right value and source sample rate as three little-endian binary64 numbers to a SHA-256 stream. It compares the count and digest, with a nonempty original stream required. The observer does not advance the machine or alter its buffers. Its report is `pcm.json` inside the corresponding checked playback capture. The longer current-model check passed for 236,434 stereo samples with identical source rates and digest; the [performance chapter](PERFORMANCE.md) records its source fingerprint and scope.

Matching this stream checks that execution batching preserves the modeled sound output. It does not establish analogue hardware fidelity, browser scheduling quality or audible full-speed music. Browser resampling happens after the source PCM boundary, and slow game execution can still starve the host output.

## Play tier: the audio microcode in TypeScript (10 November)

[`systems/n64/aspmain.ts`](../../../../systems/n64/aspmain.ts) implements the cartridge's audio microcode (the SDK's "aspMain", audio ABI 1) for the play tier only. It recognizes the microcode by FNV-1a hashes of its code span (IMEM $080–$E9F, `b649785b`) and its 704-byte data image (`6e78d7c8`). [`player.ts`](../../../../systems/n64/player.ts) sends OSTask type 1 to Fast3D and type 2 to this implementation; anything either declines runs the original instructions. Learn, ROM Desk and verification keep the reference tier.

The implementation follows the original microcode, read from the recovered RSP words, rather than another emulator's account of the ABI:

- **Dispatcher.** Commands arrive in 320-byte chunks DMA'd to DMEM $380 and are read from DMEM as they execute, through the data image's jump table at $010. A private 4 KiB DMEM mirror keeps the original layout: segments at $320, buffer state at $360, codebook at $4C0, buffers from $5C0, RESAMPLE/ENVMIXER scratch from $F90. The mirror is written back to DMEM when the task completes, so later tasks see the same stale DMEM. The start-up loop clears only segment 0: it stores to the same word sixteen times, so segments 1–15 keep earlier contents.
- **Commands.** ADPCM, CLEARBUFF, ENVMIXER, LOADBUFF, RESAMPLE, SAVEBUFF, SEGMENT, SETBUFF, SETVOL, DMEMMOVE, LOADADPCM, MIXER, INTERLEAVE and SETLOOP, plus the no-op. Each lane restates the vector arithmetic: VMULF rounding, saturation after VMACF accumulation, VSAR slices and the 48-bit accumulator's 32-bit wrap of whole units in the ADPCM predictor, and fractional slices that saturate with the high half. Loop counts match the original: whole 16- or 32-byte groups, RESAMPLE and ENVMIXER running at least one block, and A_INIT ENVMIXER one more. So do DMA sizes (8-byte aligned addresses, lengths rounded up) and the order of loads and stores where buffers overlap. ADPCM reads the next frame's header, residuals and codebook entry before storing the current frame, which matters when a header indexes past the loaded codebook into the buffers.
- **Inherited vector flags.** RESAMPLE's first VSUB consumes the RSP's VCO borrow bits left by earlier microcode, so the implementation reads `RspVector.carry` at task start and writes the final value back. On the title route VCO was zero at every audio task start. ENVMIXER's VCL clamp would read stale VCO/VCC on a non-initial call before any flag-clearing operation; the implementation declines that case.
- **Envelope.** Unknown commands, including POLEF (unused by SM64), unaligned vector buffers, and buffers overlapping the data image or reaching the scratch area are declined. So are multi-row DMA and DMA that would reach IMEM: bit 12 of a buffer address selects IMEM, as the original's DMA does. A declined task undoes its RDRAM writes, discards its DMEM mirror and runs the original microcode from the untouched machine state.

**Differential check.** [`recovery/audio-play.ts`](../recovery/audio-play.ts) runs whole audio tasks on the original RSP words, decoded by the recovery interpreter after the boot loader's copies, and through the implementation, from identical RDRAM, random stale DMEM, random vector registers and VCO. It compares every RDRAM and DMEM byte and the final VCO. The random cases cover every implemented command: counts that are not multiples of a loop, all flag combinations, extreme samples, gains, rates and codebooks, segments, in-place decoding and multi-command sequences. A small share of buffers deliberately falls outside the envelope; there the original may corrupt its own IMEM or exceed RDRAM, and the implementation must decline. Over 40 seeds × 900 cases (36,000 tasks), 31,863 ran on the implementation with identical results and 4,137 were declined with memory untouched; there were no mismatches. Earlier rounds found and fixed two real differences: the in-place codebook read order and the IMEM bit in ADPCM's state DMA. One 450-case seed is the integration test [`audio-play.integration.test.ts`](../recovery/audio-play.integration.test.ts); synthetic unit tests without cartridge bytes are in [`aspmain.test.ts`](../../../../systems/n64/aspmain.test.ts).

**Title route.** From the package's launch checkpoint (FullSync 131), the reference tier ran 2.85 billion ticks (about 30.4 seconds of guest time, 759 frames, 1,520 audio tasks). Before each audio task started, a copy of RDRAM, DMEM and VCO went through the implementation. When the original task reached BREAK, every byte it had written by SP DMA was compared, along with the absence of other implementation writes and all of DMEM. **All 1,520 tasks were identical**, covering 11,461,856 DMA-written bytes. Running the same route with the implementation completing audio tasks, all 1,520 stayed on it with no fallbacks.

**PCM and game state.** The original microcode keeps the RSP busy for about 200,000 instructions per task; the implementation completes the task when it starts, like Fast3D. That moves the SP interrupt earlier, so the audio thread's next `osAiGetLength()` read happens a few hundred ticks later; the first frame measured 492. SM64 sizes each AI buffer from the remaining length, rounded to 16 samples. Within a few audio frames one buffer has a different length (2,624 bytes against 2,560 in the trace), and the synthesized stream diverges from there (first differing stereo frame 2,860 of 972,653). Game RAM differs from the first frame boundary for the same reason. The existing play tier shows the same effect without this implementation: Fast3D and compiled blocks alone diverge from reference PCM at stereo frame 105,244.

To separate timing from arithmetic, a scratch experiment recorded each original audio task's start and BREAK ticks on the reference tier. It then replayed the route with the implementation computing each task at its start while holding the RSP busy until the recorded BREAK tick. **The replay matched the reference exactly**: PCM byte for byte and the RDRAM hash at every frame boundary. Over the full 2.85 billion ticks, all 972,653 stereo frames matched (SHA-1 `f66fa7f9…`, also the earlier reference run's). So did the RDRAM hash and tick count at all 759 frame boundaries and the final RDRAM. Graphics tasks ran the original microcode after implemented audio tasks, so on this route the graphics microcode did not depend on the vector registers that audio leaves behind. The implementation therefore produces the original microcode's output exactly; any remaining PCM difference in Play comes from task-completion timing, which SM64 feeds back into its buffer sizes.

**Limits.** The implementation does not reproduce the RSP's final vector registers, accumulators, VCC or VCE; it writes back only VCO. It also leaves IMEM holding the boot loader instead of the audio code, and leaves the SP DMA address registers and the semaphore as they were. No CPU code observed these on the measured routes. It does not honour a yield request at boot, which SM64 never makes for audio tasks. POLEF and anything outside the envelope run the original microcode. Completion is immediate rather than at the original's tick; predicting that tick would need a cycle model of the microcode and its DMA waits, which Play does not need while Fast3D and compiled blocks already change CPU timing.

## What remains

The functional scheduler gives the RSP two ticks per three CPU ticks. Cache, dual issue, pipeline and precise asynchronous timing remain unverified. Later execution produces nonzero PCM during the logo, title and menu, and completes the original audio-session reset through its thread and queue logic. The captured [title-to-opening replay](STARTUP.md) also checks processor/device/memory consistency, separately from this first task. Neither establishes audible browser music or an independent sample-by-sample hardware match. The [graphics studies](GRAPHICS.md) complete buffer clears and a textured task. The worker player remains in progress; browser sound, complete controls, saving and progression still need acceptance.
